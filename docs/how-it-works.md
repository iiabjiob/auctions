# Как работает система простыми словами

  ## Коротко

  Система сначала собирает и хранит лоты у себя в базе, потом обогащает их недостающими данными, потом считает рейтинг, и уже после этого показывает пользователю
  готовый список.

  Главная идея такая:
  не ходить на внешний сайт каждый раз, когда пользователь просто смотрит каталог, а опираться на уже сохраненные локальные данные.

  ## 4 воркера

  У нас сейчас четыре фоновых воркера:

  ### 1. Воркeр синхронизации источников

  Он отвечает за то, чтобы:

  - забирать новые лоты с площадок,
  - обновлять уже известные лоты,
  - сохранять их в локальную БД.

  Простыми словами:
  он приносит сырье.

  ### 2. Воркeр актуальности

  Он отдельно проверяет, не устарел ли лот, и обновляет lifecycle-состояние в локальной базе.

  Он:

  - переоценивает `active / expired / stale / archived`,
  - обновляет признаки актуальности на основе `last_seen_at` и дат лота,
  - сохраняет окно следующего source scan в отдельной таблице состояния и в health-данных,
  - очищает enrichment-state для неактуальных лотов.

  Простыми словами:
  он решает, лот еще живой или уже пора прятать его из активного потока.

  ### 3. Воркeр enrichment

  Он смотрит, хватает ли локальных данных для нормального рейтинга.

  Если чего-то не хватает, он:

  - ставит лот в очередь на обогащение,
  - аккуратно делает retries,
  - держит lease, чтобы два воркера не лезли в один лот одновременно,
  - учитывает priority, TTL, max attempts.

  Простыми словами:
  он добирает недостающие важные факты.

  ### 4. Воркer анализа/рейтинга

  Он пересчитывает рейтинг, когда:

  - поменялись данные лота,
  - изменились детали,
  - изменились ручные поля,
  - изменилась scoring config,
  - или включен opt-in режим с активным profile.

  Простыми словами:
  он превращает данные в рейтинг.

  ———

  ## Как считается рейтинг

  Рейтинг считается не “магией”, а по понятным блокам:

  - экономика
    цена, маржа, ROI, расходы, выгода
  - срочность
    срок подачи заявки, близость дедлайна
  - риск
    юридические сигналы, исключающие слова, статус
  - качество данных
    есть ли документы, фото, описание, важные поля
  - fit под профиль пользователя
    регион, категория, бюджет, риски, ключевые слова, дистанция

  ### Очень просто:

  Система берет лот и задает вопрос:

  > “Насколько этот лот подходит под правила и интересы пользователя, и насколько он вообще хороший по данным и экономике?”

  Потом складывает это в итоговый score.

  ———

  ## Как это работает для разных пользователей

  Система довольно гибкая.

  ### Что уже можно настраивать

  Для пользователя/компании можно задать:

  - целевые регионы
  - целевые категории
  - бюджет min/max
  - минимальный ROI
  - минимальный discount
  - допустимые legal risks
  - максимальную дистанцию
  - стоп-слова
  - желательные ключевые слова
  - стратегию: conservative / balanced / aggressive
  - веса для profile-fit

  ### Что это дает

  Один пользователь может хотеть:

  - только спецтехнику,
  - только в Московской области,
  - с бюджетом до 2 млн,
  - без высокого риска.

  Другой может хотеть:

  - любой регион,
  - более агрессивную покупку,
  - больший риск,
  - высокий потенциал прибыли.

  Система это выдерживает, потому что профиль пользователя отдельный от самих данных лота.

  ———

  ## Профили интересов и Telegram

  Профиль интересов — это персональное правило, которое говорит системе, какие лоты важны конкретному пользователю.

  Примеры:

  - “спецтехника от 2 млн рублей”;
  - “только BMW”;
  - “лоты с рейтингом от 85”;
  - “без стоп-слов и высокого юридического риска”.

  ### Чем профиль отличается от среза таблицы

  Срез таблицы — это удобный UI-фильтр для просмотра каталога прямо сейчас.

  Профиль интересов — это фоновое правило. Оно работает даже тогда, когда пользователь не открыл таблицу. Backend может взять новый лот, проверить его против активных профилей и решить, кому отправить уведомление.

  Поэтому:

  - срез помогает смотреть данные;
  - профиль интересов управляет персональными сигналами и Telegram-уведомлениями.

  Практически это работает так:

  - пользователь настраивает фильтры таблицы;
  - сохраняет их как срез, например “BMW от 2 млн”;
  - в блоке “Интересы” выбирает этот срез и подключает его к Telegram;
  - backend превращает фильтры среза в профиль интересов;
  - когда пользователь обновляет сохраненный срез, связанные Telegram-профили синхронизируются с ним.

  ### Как Telegram решает, что отправлять

  Для каждого лота система сначала строит decision report: рейтинг, рекомендация, экономика, риски и причины.

  Потом backend проходит по активным профилям интересов:

  - проверяет, совпадает ли регион / категория / бюджет / ключевые слова;
  - отсекает профиль, если есть стоп-слова или blockers;
  - проверяет минимальный рейтинг профиля;
  - проверяет, включен ли Telegram для профиля;
  - создает персональную запись в Telegram outbox только для подходящего пользователя.

  Один и тот же лот может быть отправлен одному пользователю и не отправлен другому. Например, BMW с высоким рейтингом не уйдет пользователю, который включил только спецтехнику.

  Если у пользователя подключен Telegram chat, sender отправляет сообщение в этот личный чат. Для старых глобальных уведомлений остается fallback на общий `TELEGRAM_CHAT_ID`.

  ———

  ## Насколько гибкая система сейчас

  ### Сильные стороны

  - Можно работать с разными источниками.
  - Можно подстраивать рейтинг под разные стратегии.
  - Можно работать почти целиком на локальной БД.
  - Есть защита от бесконечных повторных попыток enrichment.
  - Есть понятный hash-based механизм: если данные не менялись, пересчет не нужен.

  ### Ограничения

  - Система уже гибкая, но не “идеально enterprise” во всех краях.
  - Некоторые вещи еще остаются как переходные:
      - часть legacy fallback в scoring,
      - profile scoring пока opt-in, а не default,
      - enrichment policy еще можно усиливать.
  То есть ответ такой:
  для разных пользователей система подходит хорошо уже сейчас, но она еще в процессе зрелого enterprise-оформления.

  ———

  Система работает так:

  > источник приносит лоты → локальная база их хранит → enrichment добирает важные факты → scoring считает рейтинг под данные и профиль пользователя → grid
  > показывает готовый результат.

  ———

  ## Практически

  Если включить профиль пользователя, то система сможет по-разному ранжировать лоты для:

  - более осторожного инвестора,
  - более агрессивного покупателя,
  - пользователя, который ищет только определенный регион,
  - пользователя, которому важен ROI,
  - пользователя, которому важна юридическая чистота.

• Да. По текущей реализации система не должна ходить в первоисточник при обычном просмотре каталога. Основные обращения к внешним площадкам идут только из фоновой
  синхронизации и из явных refresh-операций.

  ## Как часто ходим во внешний источник сейчас

  ### 1. Синхронизация списка лотов

  Это главный регулярный поход в источник.

  По настройкам воркер запускается примерно:

  - каждые 12 часов
  - плюс случайный jitter до 45 минут

  То есть в норме это не постоянный опрос, а периодическая синхронизация.

  ### 2. Детальная карточка

  Детали обычно читаются из локальной базы.

  Во внешний источник мы идем только если:

  - пользователь явно нажал refresh,
  - фоновой enrichment решил, что локальных данных не хватает,
  - TTL для важного лота истек,
  - либо это отдельный worker-controlled refresh.

  То есть обычный просмотр карточки не должен дергать источник.

  ### 3. Пересчет рейтинга

  Сам пересчет рейтинга ходит только по локальной БД.
  Он не должен сам по себе тянуть внешний сайт.

  ## Что чаще всего меняется на источнике

  Ты прав: у многих лотов после публикации изменения редкие, но не нулевые.

  Обычно меняются:

  - статус лота,
  - дата окончания приема заявок,
  - цена / шаг / минимальная цена,
  - иногда состав документов,
  - иногда карточка детали.

  То есть чаще всего важны:

  - статус
  - дедлайн
  - цена
  - документы / фото / описание
    Но это зависит от площадки.

  ———

  ## Где сейчас риск лишних обращений

  С точки зрения кода, самые “опасные” места по частоте походов во внешний источник:

  1. source sync worker
     Это регулярный fetch списка лотов.
  2. explicit live refresh в detail pane
     Если часто нажимать refresh, он будет ходить наружу.
  3. enrichment worker
     Он может догружать детали, но только для лотов с нехваткой evidence, с lease/backoff/limit.
  4. actuality worker
     Он внешний источник не опрашивает, а только пересчитывает локальную актуальность и окно следующего scan.

  ———

  ## Что важно для защиты аккаунта от бана

  Если у тебя уже был бан из-за частых обращений, я бы смотрел на это так:

  ### Безопасный режим

  - держать auction_sync_run_on_start = false
  - не делать частые manual refresh
  - не включать лишний live refresh
  - держать auction_sync_limit умеренным
  - если надо, увеличить интервал синхронизации до 1 раза в сутки или хотя бы реже, чем сейчас

  ### Практический совет

  Если цель не “ловить каждое изменение мгновенно”, а просто держать каталог актуальным, то чаще всего достаточно:

  - 1–2 раза в сутки список
  - детали только по требованию или через enrichment для важных лотов

  ———

  ## Как я бы рекомендовал настроить частоту

  Если хочешь снизить риск бана, разумная стратегия такая:

  - analysis/scoring: можно часто, потому что это локально
  - manual live refresh: использовать редко

  ———

  ## Итог

  Ключевая мысль:

  > сейчас система должна быть устроена так, чтобы внешний источник дергать редко и только по делу, а не при обычной работе с интерфейсом.

  Если коротко:

  - просмотр каталога — локально
  - просмотр карточки — локально, пока сам не попросишь refresh
  - регулярное обновление списка — раз в 12 часов плюс jitter
  - детали — только точечно

  Если хочешь, я могу следующим сообщением предложить конкретную безопасную конфигурацию частот под режим “минимум банов, максимум полезности” — с цифрами для
  каждого воркера.

  ## Мой практический ответ

  ### Да, делаем первую фильтрацию

  Но фильтрация должна быть локальной, после загрузки минимального списка лотов.

  То есть:

  1. С площадки забираем список лотов
     Минимум: название, цена, статус, дедлайн, регион, категория, ссылка, id.
  2. В локальной БД делаем первичную фильтрацию
      - явные неподходящие лоты отбрасываем сразу
      - подозрительные / нерелевантные помечаем ниже
      - подходящие отправляем в enrichment / scoring
  3. Детали тянем только для перспективных лотов
      - если не хватает evidence для рейтинга
      - если лот дорогой / интересный
      - если TTL истек
      - если пользователь явно открыл карточку и запросил refresh

  ———

  ## Почему не стоит тянуть “все данные”

  Потому что это:

  - сильно увеличивает число запросов,
  - повышает риск бана,
  - замедляет sync,
  - создает много мусорных данных, которые потом все равно не нужны.

  Если тянуть все детали для всех лотов, ты фактически превращаешь систему в постоянный скрапер. Это плохая модель для стабильной работы.

  ———

  ## Почему не стоит фильтровать только на стороне площадки

  Потому что:

  - площадка обычно не знает твои реальные критерии,
  - часть полезных лотов можно отсеять слишком рано,
  - у разных пользователей разные интересы.

  Если фильтровать только на стороне source, ты потеряешь гибкость.
  Если фильтровать только локально, ты сохраняешь гибкость, но не сливаешь лишние запросы наружу.

  ———

  ## Правильная схема для твоего случая

  Я бы делал двухступенчатую модель:

  ### Уровень 1. Глобальная фильтрация

  Это фильтр для всей системы, не завязанный на конкретного пользователя.

  Например:

  - не тот источник
  - явно не тот тип актива
  - отменен / архив
  - нет цены
  - мусорный статус
  - слишком мало данных, чтобы вообще иметь смысл дальше смотреть

  Это можно считать системным “неинтересно вообще”.

  ### Уровень 2. Профиль пользователя

  Это уже персональный уровень:

  - нужные регионы
  - категории
  - бюджет
  - риск
  - ключевые слова
  - дистанция
  - стратегия

  Это не надо использовать как жесткий early-drop для всех, если у тебя будет несколько пользователей.
  Лучше использовать это в scoring / ranking, а не на этапе ingest.

  ## Что это значит для системы

  ### 1. Быстрый репорт

  Это должен быть основной пользовательский экран/выдача.

  Он строится из локальных данных:

  - базовые данные лота
  - LotEvidence
  - профиль пользователя
  - экономика
  - риск
  - дедлайн
  - profile_fit

  Итог:
  система не просто сортирует лоты, а показывает, какие из них достойны внимания прямо сейчас.

  ———

  ### 2. Telegram-канал

  Telegram лучше сделать не отдельной логикой, а вторым выходом из той же аналитики.

  То есть:

  - воркер считает рейтинг локально
  - система понимает, что лот “достоин уведомления”
  - если да, то отправляет короткое сообщение в Telegram

  ———

  ## Что нельзя делать в Telegram

  Не надо слать туда все подряд. Иначе будет шум и пользователь перестанет смотреть канал.

  В Telegram должны попадать только:

  - высокоприоритетные лоты
  - лоты с близким дедлайном
  - лоты, которые хорошо подходят под профиль
  - новые лоты с сильной экономикой
  - лоты, где изменилось что-то важное: цена, статус, дедлайн, документы

  ———

  ## Какой формат сообщения я бы рекомендовал

  Короткий и практичный:

  - название лота
  - источник
  - регион
  - цена
  - дедлайн
  - score
  - estimated ROI
  - max buy price
  - 1-3 причины, почему лот интересен
  - 1-2 риска
  - ссылка на карточку в системе

  Пример логики:

  > Экскаватор, Московская область
  > Score: 91
  > ROI: 48%
  > Max buy: 1.8 млн
  > Причины: подходит по региону, высокий дисконт, дедлайн через 2 дня
  > Риски: нужны документы, юридический риск средний

  ———

  ## Какая архитектура для этого правильная

  Я бы разделил на 3 слоя:

  ### Слой 1. Отбор

  Лот вообще достоин внимания или нет.

  ### Слой 2. Подготовка решения

  Для интересных лотов система считает:

  - экономику
  - риски
  - max price
  - fit под профиль

  ### Слой 3. Доставка

  - в UI показываем полный репорт
  - в Telegram отправляем короткий alert

  ———

  ## Важный принцип

  UI и Telegram должны использовать одну и ту же аналитику.

  Не должно быть так, что:

  - в UI один score,
  - а в Telegram другой,
  - а в воркере третий.

  Должна быть одна нормализованная оценка, а потом уже два канала доставки:

  - интерфейс
  - уведомление

  ———

  ## Что я бы сделал дальше

  Для твоего сценария логично добавить 3 сущности результата по каждому лоту:

  1. Decision summary
      - короткая выжимка для пользователя
  2. Action recommendation
      - смотреть / считать / подавать / игнорировать
  3. Notification eligibility
      - отправлять ли в Telegram

  ———

  ## Практическое правило для Telegram

  Я бы сделал Telegram не на все лоты, а только когда выполняется хотя бы одно условие:

  - score выше порога
  - profile_fit высокий
  - дедлайн близко
  - ROI выше порога
  - новый лот и он сразу интересный
  - изменился статус на более важный

  И обязательно:

  - дедупликация
  - лимит на число сообщений
  - не слать один и тот же лот многократно без существенного изменения

  ———

  ## Итог

  Для твоего будущего продукта правильная форма такая:

  > система не просто хранит лоты, а помогает быстро принимать решение;
  > UI дает полный репорт, Telegram дает короткий сигнал по самым интересным лотам.

  Это очень хорошая цель для текущей архитектуры, и она уже почти туда ведет.

  Если хочешь, я могу следующим сообщением предложить конкретную схему “быстрого репорта” по лоту: какие поля там должны быть, в каком порядке, и как из этого
  делать Telegram-сообщение.
